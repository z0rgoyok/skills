Каждый handoff сохранить отдельным append-only файлом до отправки исполнителю. Основной план содержит только реестр и ссылки. После сжатия контекста перечитать активный файл; перед review перечитать файлы, по которым создавался проверяемый срез, и сверить их SHA-256.

## Общий цикл каждого пакета

1. Наблюдаемый BDD-сценарий и один минимальный RED.
2. RED-review; тот же `RED ACCEPT` разрешает атомарные RED commit/push; исполнитель возвращает один receipt, Макс проверяет remote SHA.
3. Минимальная реализация до GREEN.
4. Узкие проверки по карте риска и полный staged review тем же Максом.
5. Тот же `STAGED ACCEPT` разрешает атомарные GREEN commit/push; исполнитель возвращает один receipt, Макс проверяет remote SHA.
6. Следующий пакет только после опубликованного GREEN.

## Этап N. Название результата

Продуктовый результат и граница этапа.

### RED

Точный тест, ожидаемая предметная причина падения, проверяемое поведение или анти-поведение и команда запуска.

### Реализация

Минимальные изменения, владельцы данных и запрещённые расширения.

#### Рекомендуемая implementation map

Карта является подробным исходным маршрутом по evidence, доступному до coding. Она не требует предварительной коррекции плана при доказуемой внутренней адаптации, которая сохраняет поведение, acceptance, границу пакета и устойчивые контракты.

- архитектура и дерево затрагиваемых модулей;
- ответственность модулей и направление зависимостей;
- точные рекомендуемые файлы `create` / `edit` / `delete` / `leave unchanged`;
- ожидаемые типы, функции, методы, поля, exports и связи;
- порядок интеграции с production path;
- ключевой алгоритм или псевдоконтракт;
- подтверждённые факты;
- предположения, которые coding может уточнить;
- допустимый коридор внутренних отклонений;
- изменения требований или устойчивых контрактов, которые требуют возврата к Максу.

### Приёмка

Матрица поведения и анти-поведения по применимому `$core-qa`: основные результаты, границы, запреты, отказы, изоляция, повтор/порядок, допустимые и запрещённые эффекты, сохраняемые инварианты, точные тесты и evidence чувствительности. Для каждого неприменимого или перенесённого класса указать причину.

### Граница коммита

Для RED, GREEN и принятой correction-стадии отдельно указать неизменяемую границу поведения, точный staged tree, пути и артефакты коммита, commit/push handoff, hook evidence, локальный commit SHA и подтверждённый remote SHA. Явно перечислить исключённые соседние области.

### Принятые отклонения реализации

После staged review записать только отклонения от рекомендуемой карты, значимые для следующих пакетов или будущего сопровождения. Локальные детали, не меняющие дальнейшие решения, оставить в handoff/evidence ревью.
