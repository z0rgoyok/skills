# Commit и push принятой стадии

Читать этот файл только при подготовке `RED ACCEPT`, `STAGED ACCEPT` или принятой correction-стадии.

## Встроить публикацию в ACCEPT

В том же review-ответе дать короткий исполнимый блок:

- принятая стадия, staged hash и tree OID;
- точный состав коммита и запрещённые примеси;
- commit message;
- уже выполненные проверки и решение по hooks;
- commit-команда;
- проверка равенства нового `HEAD^{tree}` принятому tree OID;
- remote, branch/ref и push-команда без force;
- формат одного publish receipt;
- следующий содержательный шаг после успешного push.

Ориентир — 20–40 строк. Не создавать отдельный publish-handoff-файл, не копировать QA-матрицу, архитектуру, полный diff и implementation-handoff. Основной план обновить по receipt одной компактной записью: стадия, commit SHA, remote/ref, результат push.

## Учитывать hooks во время review

Исполнитель передаёт результаты проверок вместе со staged-срезом. Макс сопоставляет их с hooks до выдачи verdict. Отдельную фазу инвентаризации не создавать.

При первом review прочитать фактические commit/push hooks и wrapper-команды. Сохранить в управляющем статусе их paths и hashes. На следующих стадиях использовать прежнюю инвентаризацию, пока hashes и конфигурация не изменились.

Hook, поддерживающий штатный `--no-verify`, обязательно пропустить, если каждая его проверка уже выполнена над той же порцией работы:

- commit-hook — над принятым staged tree и, если нужно, тем же сообщением;
- push-hook — над точным диапазоном commits, remote и ref;
- hook, читающий всё дерево, — при совпадающем staged/unstaged/untracked state;
- mutating-hook — после эквивалентного преобразования и повторной фиксации принятого snapshot.

Для RED semantic test должен падать по принятой бизнес-причине, а остальные проверки hook — проходить. Похожая команда, прежний snapshot или более узкий scope эквивалентностью не считаются.

Если хотя бы одна policy-, secret-, signing-, message-, generated-, security- или другая проверка не покрыта, выполнить hook. `git commit --no-verify` допустим только при полном покрытии одновременно `pre-commit` и `commit-msg`. `prepare-commit-msg`, `post-commit` и серверные hooks не отключать. `git push --no-verify` использовать при полном покрытии `pre-push`.

## Выполнить атомарную публикацию

Исполнителю без промежуточного запроса:

1. Выполнить назначенный commit.
2. Получить commit SHA и `HEAD^{tree}`.
3. Убедиться, что tree совпадает с принятым staged tree OID.
4. Выполнить push без force.
5. Вернуть одним сообщением команды, hook decisions, commit/tree SHA, push result, remote/ref и итоговое состояние дерева.

Успешный push завершает публикацию. Макс не перепроверяет remote и сразу готовит следующий RED/GREEN-handoff либо финальное ревью. Опубликованный стадийный commit не amend/rebase/reset и не переписывать force-push; исправление выпускать новым reviewable commit.
