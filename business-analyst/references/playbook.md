# Словарь бизнес-анализа и рабочие артефакты

Применяй выборочно. Таблица ID ниже — локальная конвенция при отсутствии существующей; это не обязательный стандарт BABOK или трекера.

## Вокабуляр

| Термин | Рабочее значение |
| --- | --- |
| Elicitation | Выявление потребностей через документы, наблюдение, вопросы и совместный разбор; не механическое переписывание пожеланий. |
| Stakeholder / SME | Заинтересованная сторона / эксперт предметной области. Экспертиза не обязательно даёт право утверждения. |
| AS-IS / TO-BE / gap analysis | Текущее состояние / целевое состояние / анализ необходимого изменения между ними. |
| Business capability / process | Что организация умеет делать / как работа проходит через действия и роли. |
| BR / SR | Бизнес-цель изменения / потребность заинтересованной стороны. |
| FR / NFR | Требуемое поведение решения / измеряемые свойства и условия его работы. Это подвиды solution requirements. |
| Transition requirement | Временная потребность для перехода: миграция, обучение, сосуществование и непрерывность работы. |
| Business rule / constraint | Политика или правило предметной области / ограничение допустимых вариантов решения. |
| Domain model / glossary | Бизнес-сущности и отношения / согласованные значения терминов. Это не физическая схема БД. |
| Use case / user story | Сценарий достижения цели / краткая потребность через actor, need и value. Оба требуют проработки поведения. |
| Acceptance criteria / UAT | Проверяемые условия принятия результата / приёмочные проверки в бизнес-контексте. |
| Verification / validation | Правильно ли сформулированы требования / нужны ли именно эти требования для бизнес-цели. |
| Traceability / RTM | Связи происхождения, реализации и проверки / представление этих связей в матрице. |
| Baseline / change request | Зафиксированная согласованная версия / предложение её изменить с анализом влияния. |
| Decision table / state model | Условия и результаты бизнес-решения / состояния и допустимые переходы. |
| RACI / decision owner | Распределение выполнения, ответственности, консультации и информирования / уполномоченный владелец конкретного решения. Не назначай их без основания. |
| Scope creep / impact analysis | Неконтролируемое расширение области / анализ последствий предлагаемого изменения. |

## ID и статусы

При отсутствии схемы используй префикс инициативы: `PAY-BR-001`, `PAY-SR-001`, `PAY-FR-001`, `PAY-NFR-001`, `PAY-TR-001`, `PAY-RULE-001`, `PAY-AC-001`, `PAY-CR-001`. Существующие product objective ID можно связать с BR без дублирования цели. ID не перенумеровывай при смене порядка.

Разделяй две оси: статус требования (`draft / in-review / approved / superseded`) и evidence реализации (`not-checked / planned / implemented / verified`). Приводи основание для approved и verified. Реализованное, но неутверждённое поведение возможно; не прячь это сочетание.

## Синтетический пример: отмена заявки

В учебном примере предложены, но не утверждены правила: `PAY-RULE-001` — владелец может отменить заявку только в статусе `Draft`; `PAY-RULE-002` — повтор отмены уже отменённой заявки возвращает её состояние без повторного эффекта. Реальный проект должен отдельно подтвердить эти правила.

Предложенное `PAY-FR-001`: «Когда владелец запрашивает отмену заявки в статусе Draft, система переводит её в Cancelled и делает этот результат доступным владельцу».

```gherkin
Scenario: Владелец отменяет черновик
  Given заявка принадлежит пользователю и имеет статус Draft
  When владелец запрашивает отмену
  Then заявка имеет статус Cancelled
  And владелец получает подтверждение отмены

Scenario: Повторная отмена
  Given заявка владельца уже имеет статус Cancelled
  When владелец повторно запрашивает отмену
  Then заявка остаётся в статусе Cancelled
  And новые побочные эффекты отмены не возникают
```

До передачи также проработай чужую заявку, иные статусы и конкурентную смену состояния. «Не создавать повторный эффект» — требование к наблюдаемому поведению; конкретный механизм идемпотентности выбирает архитектура.
