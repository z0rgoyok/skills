# Semantic Duplication Audit

## Результат

Провести read-only аудит выбранной области репозитория и выдать проверяемую карту всех найденных кластеров. Для каждого кластера указать точные файлы и символы, общий смысл, намеренные различия и решение: объединить, упростить локально или оставить раздельным.

Slopo ищет кандидатов. Он не решает, является ли похожий код нежелательным дублем. Не изменять код, зависимости, CI, конфигурацию проекта и внешние системы, пока пользователь отдельно не попросит реализовать выводы.

## Порядок работы

1. Прочитать инструкции репозитория и применимые навыки языка, архитектуры и качества.
2. Зафиксировать корень Git, ревизию, ветку и состояние рабочего дерева. Незакоммиченные изменения входят в анализ; явно сказать об этом или перейти в чистое рабочее дерево.
3. Определить реальную область анализа по отслеживаемым файлам. Разделять по отдельным прогонам:
   - разные приложения или крупные модули;
   - production-код и тестовую инфраструктуру;
   - рукописный и сгенерированный код;
   - языки с разными архитектурными границами.
4. Проверить поддержку языка закреплённой версией Slopo. Если важная часть проекта не поддерживается, назвать аудит частичным и не делать вывод об отсутствии дублей.
5. По умолчанию использовать локальную модель Ollama. Не отправлять закрытый код внешнему embedding-провайдеру без явного согласия пользователя.
6. Выбрать режим:
   - для разовой read-only проверки прочитать [локальный запуск Slopo](references/slopo-workflow.md) и запустить `scripts/run_slopo_audit.sh`;
   - если пользователь просит настроить проект для повторных запусков, прочитать [постоянный профиль проекта](references/project-setup.md), создать профиль через `scripts/setup_project_profile.sh`, проверить diff и выполнить первый запуск через `scripts/run_project_profile.sh`.
   Основной и мягкий отчёты должны использовать одну БД и одни эмбеддинги.
7. Прочитать [ручной архитектурный разбор](references/review-method.md). Проверить каждый кластер выбранного отчёта по полному исходному коду, вызовам и направлениям зависимостей.
8. После содержательного совпадения искать теми же символами, полями и инвариантами места, которые Slopo не связал с кластером. Явно разделять:
   - участников кластера Slopo;
   - связанные места, найденные вручную.
9. Подготовить итог по формату из `references/review-method.md`. Пути нужны для всех кластеров, включая отклонённые. Номер кластера без списка кода недостаточен.

## Обязательные ограничения

- Создавать БД, конфигурацию и отчёты только во временном каталоге с закрытыми правами.
- В постоянном режиме хранить локальную БД и отчёты только в игнорируемом `.slopo/local/`; конфигурацию и проверенные hash исключений можно коммитить.
- Исключать зависимости, vendor, build output, минифицированный и сгенерированный код. Тесты по умолчанию анализировать отдельным прогоном, а не смешивать с production-кодом.
- Записывать версию Slopo, модель, размер embedding, пороги, исключения, Git SHA и состояние рабочего дерева.
- Не считать score вероятностью дефекта. Номер кластера служит только ссылкой внутри конкретного отчёта.
- Не определять приоритет размером кластера. Сначала учитывать безопасность, целостность данных, пользовательское рассогласование и частоту совместных изменений.
- Не создавать `utils`, `common`, `shared` или общий helper только ради совпадения строк. Объединять одно знание с совместимым владельцем и причиной изменения.
- Не публиковать полный отчёт с закрытым исходным кодом. Во внешнем или публичном результате оставлять метаданные, пути, символы и выводы без больших фрагментов исходников.
- Для тренда сравнивать только один проект с собственной базовой линией при неизменных модели, версии, порогах, области и исключениях. Сырые проценты разных проектов несопоставимы.

## Завершение

Сохранить нужные числа, хеши кластеров и выводы. После проверки можно удалить только точный временный каталог, напечатанный скриптом. Если Ollama запускался для аудита вручную, остановить только запущенный процесс; загруженную модель не удалять без отдельной просьбы.
